# PRD：会议实时 AI 分析引擎

> 版本 1.0 — 2026-09-17  
> 状态：需求评审

---

## 1. 背景与动机

### 1.1 现状问题

当前 Meetings 工作台已具备：
- 实时语音转写（ASR，支持 4 个服务商）
- 手动记录摘要、关键结论、行动项
- 会议历史管理与导出

**缺失的核心能力**：会议进行中的实时智能分析。参会者需要在会议中同时完成「听」「理解」「思考应对」「记录」四件事，认知负荷极高。尤其在谈判、评审、答辩等高压场景中，容易遗漏关键信息或错失最佳回应时机。

### 1.2 目标用户

| 角色 | 典型场景 | 核心痛点 |
|------|---------|---------|
| 产品经理 | 需求评审会 | 对方说「这个需求很简单」，背后可能是范围蔓延的信号 |
| 销售/BD | 客户商务谈判 | 需要实时识别对方的真实意图和底线 |
| 咨询顾问 | 客户访谈 | 快速提炼客户表述中的核心诉求和隐含需求 |
| 管理者 | 团队周会/复盘 | 从多人发言中提炼关键决策和风险点 |
| 律师/合规 | 合同谈判 | 识别对方条款中的风险点和逻辑漏洞 |

### 1.3 产品定位

**不是**：会议纪要工具（已有飞书妙记、通义听悟等）  
**是**：会议中的实时 AI 参谋 — 帮你在会议进行中看清局势、找到漏洞、准备话术

## 2. 核心功能需求

### 2.1 实时要点总结（Key Points Extractor）

**触发方式**：ASR 转写产生新文本时，自动触发增量分析  
**分析频率**：每积累 3-5 条新转写（或每 30 秒）触发一次  
**输出内容**：

```
┌─────────────────────────────────────────┐
│  📋 当前要点                              │
│                                          │
│  1. 张明提出 Q3 上线时间可能延迟 2 周     │
│     ↳ 原因：前端人力不足，需借调 1 人      │
│                                          │
│  2. 李华要求增加数据导出功能               │
│     ↳ 优先级：高，客户合同中有明确要求      │
│                                          │
│  3. 王芳对技术方案的安全性提出质疑          │
│     ↳ 关注点：用户数据加密方案未确定        │
│                                          │
│  [上次更新: 12:34:56]                     │
└─────────────────────────────────────────┘
```

**关键约束**：
- 要点数量上限 10 条，超出时合并/淘汰旧要点
- 每条要点标注来源（说话人 + 时间戳）
- 支持手动删除/编辑要点
- 要点随会议进展动态更新（不是追加，而是刷新）

### 2.2 实时观点分析（Viewpoint Analyzer）

**触发方式**：检测到明确观点表述时触发（如「我认为」「建议」「必须」「不应该」等）  
**分析维度**：

```
┌─────────────────────────────────────────┐
│  🔍 观点分析                              │
│                                          │
│  观点：「这个功能两周内就能做完」           │
│  说话人：张明 · 12:35                     │
│                                          │
│  ── 表面含义 ──                           │
│  承诺两周内完成功能开发                     │
│                                          │
│  ── 隐含意思 ──                           │
│  • 可能在低估复杂度以争取项目通过           │
│  • 未提及测试和联调时间                    │
│  • 与上次会议提到的「需要一个月」矛盾       │
│                                          │
│  ── 逻辑漏洞 ──                           │
│  ⚠️ 未考虑依赖方接口联调时间               │
│  ⚠️ 未包含代码审查和灰度发布周期           │
│  ⚠️ 与历史同类功能开发周期（4周）不符       │
│                                          │
│  ── 建议应对话术 ──                       │
│  💬 「两周开发可以，但我们需要明确联调和     │
│     测试的时间安排，能否拆解一下里程碑？」   │
│                                          │
│  💬 「上次提到需要一个月，是什么因素        │
│     让时间缩短了？我们可以对齐一下。」      │
│                                          │
│  [有用 👍] [有误 👎] [忽略 ✕]             │
└─────────────────────────────────────────┘
```

**分析框架**：
- **表面含义**：观点的直接表述
- **隐含意思**：说话人可能的真实意图、未说出口的前提
- **逻辑漏洞**：论证中的逻辑缺陷、数据不一致、遗漏的关键因素
- **应对话术**：2-3 个可选回应策略（温和追问、直接质疑、转移焦点）

**关键约束**：
- 每次分析展示最近 1 个观点的完整分析（避免信息过载）
- 历史分析结果折叠为列表，可展开查看
- 用户可标记分析结果「有用/有误」，用于后续优化
- 分析结果可一键复制到剪贴板

### 2.3 观点漏洞检测（Logic Flaw Detector）

这是观点分析的核心子模块，独立出来强调其重要性。

**检测维度**：

| 维度 | 说明 | 示例 |
|------|------|------|
| 数据矛盾 | 与会议中已有数据/结论矛盾 | 「上次说需要1个月，现在说2周」 |
| 逻辑跳跃 | 结论缺乏充分论据支撑 | 「竞品都有这个功能，所以我们也必须做」 |
| 隐含假设 | 未明确声明的关键前提 | 「这个方案零成本」（忽略了人力成本） |
| 偷换概念 | 讨论中概念被悄然替换 | 从「用户体验」偷换为「开发效率」 |
| 以偏概全 | 用个别案例推导普遍结论 | 「A 客户反馈了这个，说明所有客户都需要」 |
| 时间错位 | 用过去数据推断未来趋势 | 「去年增长 50%，今年也能」 |

**输出格式**：
```
⚠️ 漏洞类型：数据矛盾
📝 具体描述：张明本次承诺 2 周完成，但 08/15 会议中明确表示需要 4 周
🔗 关联证据：[08/15 14:32 张明: "这个功能至少需要一个月"]
💡 建议追问：「时间从4周缩短到2周，是技术方案有变化还是范围有调整？」
```

### 2.4 应对话术生成（Response Generator）

**触发方式**：
- 观点分析时自动生成 2-3 个话术选项
- 用户可点击任意转写文本，手动触发「生成应对话术」
- 用户可点击「全局策略」按钮，基于当前会议全局态势生成策略建议

**话术风格**：

| 风格 | 适用场景 | 示例 |
|------|---------|------|
| 温和追问 | 需要更多信息时 | 「能展开说说为什么时间能缩短吗？」 |
| 数据反驳 | 有明确数据支撑时 | 「根据上次评估，同类功能用了4周」 |
| 转移焦点 | 需要回避正面冲突时 | 「这个点很重要，我们先记录下来，会后详细讨论」 |
| 共识确认 | 需要锁定承诺时 | 「所以确认一下，两周内完成开发，对吗？」 |
| 风险提示 | 发现潜在风险时 | 「如果两周没完成，备选方案是什么？」 |

## 3. AI 服务接入设计

### 3.1 架构原则

与 ASR 模块保持一致的 BYOK（Bring Your Own Key）模式：
- 用户自选 LLM 服务商
- 用户填入自有 API Key
- 凭证仅存 localStorage
- 未配置时 AI 分析功能不可用，但不影响转写和手动记录

### 3.2 支持的 LLM 服务商

| 服务商 | 产品 | 价格 | 优先级 | 理由 |
|--------|------|------|--------|------|
| DeepSeek | DeepSeek Chat API | ¥1/百万 token | P0 | 性价比最高，中文能力强 |
| 月之暗面 | Kimi (Moonshot) | ¥0.01/千 token (mo-32k) | P1 | 长上下文支持好 |
| 智谱 AI | GLM-4 | ¥0.1/千 token | P2 | 国产大模型，生态成熟 |
| 阿里云 | 通义千问 | ¥0.008/千 token | P3 | 与 ASR 阿里云可复用凭证 |
| 硅基流动 | SiliconFlow | 免费额度 + 按量 | P4 | 聚合平台，支持多模型 |

### 3.3 Prompt 工程

分析引擎的核心 Prompt 模板（以观点分析为例）：

```
你是一位资深的会议分析顾问。请分析以下会议发言：

## 会议背景
- 会议主题：{{meeting_title}}
- 已进行时长：{{duration}}
- 参会人：{{participants}}

## 近期转写记录
{{recent_transcript}}

## 当前发言
说话人：{{speaker}}
发言内容：「{{current_text}}」

## 请输出以下分析（JSON 格式）

1. **表面含义**：这句话的直接意思是什么？
2. **隐含意思**：说话人可能的真实意图是什么？有哪些未说出口的前提？
3. **逻辑漏洞**：论证中有哪些逻辑缺陷？与会议中已有信息是否矛盾？
4. **应对话术**：给出 2-3 个不同风格的回应建议（温和追问/数据反驳/风险提示）

注意：
- 结合会议上下文分析，不要脱离语境
- 隐含意思要基于合理推断，标注确信度
- 逻辑漏洞要具体，指出与哪些已有信息矛盾
- 话术要自然，适合会议口语场景
```

### 3.4 增量分析策略

为避免 API 调用过于频繁和 token 消耗过大：

| 策略 | 说明 |
|------|------|
| 滑动窗口 | 每次发送最近 10 条转写作为上下文 |
| 去重分析 | 已分析过的转写不重复发送 |
| 批量触发 | 每 3-5 条新转写或 30 秒触发一次 |
| 增量摘要 | 超过 20 条时，先对旧转写做摘要压缩 |
| 防抖控制 | 同一观点 10 秒内不重复分析 |

## 4. 数据模型扩展

### 4.1 Meeting 对象新增字段

```js
{
  // 现有字段保持不变
  id, title, status, participants, transcript, summary, keyPoints, actionItems, ...

  // 新增字段
  analysis: {
    keyPoints: [          // AI 提取的实时要点
      {
        id: string,
        content: string,       // 要点内容
        speaker: string,       // 来源说话人
        timestamp: number,     // 会议内时间戳
        confidence: number,    // AI 确信度 0-1
        createdAt: number,
        updatedAt: number
      }
    ],
    viewpoints: [         // 观点分析历史
      {
        id: string,
        originalText: string,  // 原始发言
        speaker: string,
        timestamp: number,
        surface: string,       // 表面含义
        hidden: string,        // 隐含意思
        flaws: [               // 逻辑漏洞列表
          {
            type: string,      // 漏洞类型
            description: string,
            evidence: string,  // 关联证据
            suggestion: string // 建议追问
          }
        ],
        responses: [           // 应对话术
          {
            style: string,     // 温和追问/数据反驳/...
            text: string
          }
        ],
        feedback: null | 'useful' | 'wrong',  // 用户反馈
        createdAt: number
      }
    ],
    lastAnalysisAt: number,   // 上次分析时间
    analysisWindow: number    // 当前分析窗口起始位置
  }
}
```

## 5. 非功能需求

### 5.1 性能
- AI 分析请求异步执行，不阻塞 UI
- 分析结果流式展示（如果 API 支持 SSE）
- 单次分析请求超时 30 秒
- 分析失败自动重试 1 次，失败后静默降级

### 5.2 成本控制
- 显示当前会议已消耗 token 数和预估费用
- 用户可设置单次会议 token 上限
- 提供「精简模式」（减少分析频率）和「深度模式」（更频繁分析）

### 5.3 隐私
- 转写内容仅发送给用户选择的 LLM 服务
- 不存储到任何第三方服务器
- 会议结束后，分析上下文立即清除
- API Key 加密存储（简单 XOR + base64）

### 5.4 降级策略
- 未配置 AI → AI 分析面板显示配置引导
- API 调用失败 → 显示错误提示，不影响转写
- 网络中断 → 暂停分析，恢复后继续
- Token 超限 → 提示用户，暂停分析

## 6. 功能优先级

| 优先级 | 功能 | 理由 |
|--------|------|------|
| P0 | AI Provider 抽象层 | 基础设施 |
| P0 | 实时要点总结 | 最高频需求 |
| P0 | 观点分析 + 隐含意思 | 核心差异化能力 |
| P1 | 逻辑漏洞检测 | 观点分析的深化 |
| P1 | 应对话术生成 | 实用价值高 |
| P2 | AI 设置界面 | 配置入口 |
| P2 | Token 用量统计 | 成本控制 |
| P3 | 分析结果导出 | 会后复用 |
| P3 | 自定义分析 Prompt | 高级用户定制 |

## 7. 成功指标

| 指标 | 目标 | 衡量方式 |
|------|------|---------|
| 分析延迟 | < 5 秒 | 从转写完成到分析结果展示 |
| 分析准确率 | > 80% | 用户标记「有用」的比例 |
| API 成本 | < ¥0.5/小时 | 单次会议平均消耗 |
| 功能采用率 | > 30% | 开启 AI 分析的会议占比 |
